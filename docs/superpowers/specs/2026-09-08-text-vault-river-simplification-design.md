# Text Vault 河流视图简化设计

## 目标

把当前 MVP 收缩成一个可以立即日用、容易阅读的普通网页应用，同时保留未来“数据 → 查询 → 视图”的稳定扩展方向。实现优先依靠少量明确状态和单向数据流，不为尚不存在的视图预建框架。

## 页面

页面只有三个纵向区域：

1. 顶部 4px 全局保存状态条；
2. 中间平级全文条目河流；
3. 底部搜索框与新增按钮。

搜索框永远只搜索。输入时立即过滤，查询写入 URL fragment；新增永远只由按钮触发。页面不再包含模式命令、Vim 快捷键或改密入口。

选中条目正文后，在浏览器选区附近显示一个小型“新标签搜索”按钮。点击后用选中文字生成 `#q=` URL 并在新标签页打开；选区消失或点击别处后按钮消失。

## 编辑规则

- 点击已有条目正文，切换为原地 textarea。
- 点击新增按钮，在河流末尾显示临时空 textarea 并聚焦。
- textarea 的输入只更新当前页面内存草稿，不逐键保存服务器。
- 点击当前编辑区以外的位置时提交草稿，然后异步保存服务器。
- 修改后的文本为空也允许保存；只有新增草稿为空白时丢弃。
- 编辑期间搜索框保持可见，但禁用搜索和新增，防止当前编辑对象从视图中消失。
- 保存状态：草稿编辑中为绿色，保存中为灰色，保存成功与背景融合，失败为红色。
- 页面离开时若草稿或 repository 尚有未保存变化，使用浏览器原生离开提醒。

## 代码边界

稳定的数据流是：

```text
repository objects → runQuery(query, objects) → river renderer
                           ↑                       ↓
URL query adapter          └──── user events ─────┘
```

- `app.js`：认证、解锁以及具体模块装配。
- `repository.js`：内存对象集合及变化通知，不包含搜索和 DOM。
- `core/query.js`：纯查询函数；当前只处理全文条目查询。
- `views/river.js`：唯一视图，持有少量 UI 状态（搜索词、正在编辑的 ID、草稿），把明确的用户操作调用到 repository、save 和 sync。
- `save.js` / `sync.js`：服务器持久化和增量读取。
- `browser/query-location.js`：URL 查询读写和新标签 URL 生成。

删除当前只为单一视图增加绕行的 `application/workspace.js`、`modes.js`、`features/vim-keymap.js`、`features/change-password.js` 和 `views/registry.js`。只有真正出现第二种视图时才引入视图注册器。

未来增加结构化对象时扩充对象种类；增加查询能力时扩充 QuerySpec 与纯查询函数；增加地图、表格或音乐视图时新增独立 renderer。视图声明以后可以作为数据保存，但 renderer 始终是受信任源码，不允许数据直接执行 JavaScript。

点击、输入和文本选择是界面的默认交互，不作为一种需要命名的特殊模式。未来若增加键盘加速，它只是附加入口，不改变页面结构和数据流。

## 测试和源码布局

浏览器端源码目录不放测试文件。所有 JavaScript 单元测试迁到 `tests/unit/`，端到端主流程保留在 `tests/e2e/`。Go 测试遵循 Go 工具约定继续与对应包相邻。

测试只覆盖稳定边界和日用主流程：查询、加密/保存/同步、点击新增、点击编辑、点击外部保存、实时搜索和选区新标签。它们用于验证设计推演的结果，不让测试结构进入产品架构，也不为每个实现细节建立测试。

## 不做

- 不实现改密 UI、命令输入、Vim 模式和键盘导航。
- 不实现多个视图、视图注册器、用户自定义视图或结构化属性。
- 不改变现有加密格式、SQLite schema、API 和备份方式。
- 不做数据库迁移或兼容层。
